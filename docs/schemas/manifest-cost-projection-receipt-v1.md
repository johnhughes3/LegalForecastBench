# Manifest cost projection receipt v1

`legalforecast.manifest_cost_projection_receipt.v1` is the canonical provider-free receipt emitted by `legalforecast acquisition project-manifest-cost` from a complete verified freeze bundle and its immutable manifest-run root.

The issuer authenticates the frozen owner manifest, verbatim owner approval, no-tool 100-case and exact 200-packet Cartesian run (`full_packet` and `metadata_only` once for each signed-manifest candidate/case mapping), run-input manifest, official model registry, prompt replay contract, exact complete amendment chain, and every packet's exact bytes through descriptor-safe single-link reads. The receipt commits those raw inputs by lowercase SHA-256 and byte length; records the requested model keys, ablations, case order, repeat sample, repeat count, optional dispatch ceiling, and matrix limit; and carries the full matrix, provider matrices and counts, case count, authenticated packet count, model/ablation cell count, aggregate matrix-row/request count, repeat-expanded attempt count, per-cell shard-row count, model count, long-context warning rows, projected model cost, and recommended two-times early-warning ceiling.

The local aggregate approval projection uses all four frozen successor models and both authenticated ablations: eight cells and 800 matrix rows/requests for 100 cases. Its `matrix_limit` is therefore at least 800 (and the CLI default is 800). Official live execution is shard-only: each of the eight model/ablation dispatches requests exactly one cell and produces exactly 100 matrix rows, below GitHub's per-shard 256-row limit. The receipt distinguishes `packet_count` (the 200 authenticated packet inputs), `case_count` (100), `cell_count`, `matrix_row_count`, `shard_matrix_row_count`, and `request_count`; `attempt_count` separately reflects repeat expansion used in cost projection.

Cost uses the official workflow formula `(input_tokens * input_token_price + max_output_tokens * output_token_price) / 1_000_000` for each packet/model row, multiplied by the row repeat count. Packet tokens use this fallback order: `estimated_input_tokens`, `input_tokens`, `prompt_tokens`, `estimated_prompt_tokens`, `packet_token_count`, `token_count`, then `ceil(packet_size_bytes / 4)`. When a registry entry declares `long_context_surcharge`, input and output prices are multiplied by its registry values only when `input_tokens` is strictly greater than `threshold_input_tokens`; packets above 272,000 estimated input tokens remain warning rows in the receipt.

The projected and recommended USD fields are fixed six-place decimal strings, while an optional operator-supplied dispatch ceiling retains its accepted decimal spelling. The optional ceiling must be at least the exact unrounded projection and no more than twice that projection. It is an early-warning control, not a provider or account cap.

`receipt_sha256` is the SHA-256 returned by `hash_payload` over the canonical top-level receipt after removing only `receipt_sha256`. Issuance stages and verifies exact canonical bytes under a pinned parent-directory descriptor, rechecks every authenticated input immediately before the no-replace hard-link commit boundary, and then rechecks both sources and the requested parent/path/inode after the link. Any post-link verification failure removes only the issuer's linked inode through the retained directory descriptor, so a failed issuance leaves no stale final receipt. It performs no provider call, AWS action, spend reservation, packet mutation, dispatch, or publication of benchmark results.

## Supplementary sibling card

`legalforecast.manifest_cost_projection_supplementary_receipt.v1` is the post-anchor supplementary variant, emitted by the same command under `--supplementary`. It is a **separate card, not this one with an added field**: Cycle 1 change control freezes whole-card authenticated bytes, so the official receipt above keeps byte-identical field sets and every already-issued official execution scope that commits to one stays valid.

The supplementary card carries every field above plus `supplementary_binding`, which records both bindings explicitly rather than leaving either inferable: `execution_mode` (always `supplementary_post_anchor`), `official_freeze_bundle_sha256` and `official_model_registry_sha256` for the official contract being reused, `official_evaluation_release_anchor`, the `corpus_anchor` derived from the run-input decision dates, `supplementary_model_registry_sha256` for the registry under evaluation, and the sorted `supplementary_model_keys` it authorizes.

Issuance requires the official freeze bundle and an independent raw-file digest pin for it. The sibling freeze must reuse the official bytes for every frozen artifact except `model_registry`, `provider_cycle_caps`, and `execution_policy`, and must differ on `model_registry`; the reference bundle must itself bind the registry the shared prompt contract commits. Every model in the registry under evaluation must classify `supplementary_post_anchor` against the corpus-derived anchor, using the same classification the official aggregate applies, so the two cannot disagree about which set a model belongs to.

Both directions refuse. Official mode rejects a sibling freeze exactly as it did before this card existed, and supplementary mode rejects the official freeze, an official-classing registry, a drifted shared artifact, and a reference bundle that does not match its digest pin. Because `schema_version` sits inside the hashed payload, a receipt cannot be re-labelled into the other lane without breaking `receipt_sha256`.

The execution scope has the same split: `legalforecast.execution_scope.v1` for official shards and `legalforecast.execution_scope_supplementary.v1` for supplementary ones, the latter carrying the same `supplementary_binding` copied verbatim from its receipt. Every consumption point — the dispatch pre-credential check, the provider cell, the shard-receipt writer, and fan-in — selects the expected card by identifier and defaults to official.

The two cards' `owner_evidence` also differs, and this is the only field-set difference besides `supplementary_binding`. The official card embeds `raw_observation_base64`, the whole captured `bd comments <bead> --json` payload. The supplementary card publishes `raw_observation_sha256` instead and refuses `raw_observation_base64` by name: the payload is every comment on the approval bead, so it carries unbounded bystander content and re-hashes the scope whenever anyone comments, and a supplementary scope has to be safe to commit to this public repository because that is the only route by which an operator-produced one reaches S3. The bounded owner approval sentence stays, as `raw_comment` with `raw_comment_sha256`, so a holder of the original capture verifies the whole chain against the published digests. Verification that is given the captured payload replays it in full; verification holding only the card re-derives every field the approval sentence determines.
