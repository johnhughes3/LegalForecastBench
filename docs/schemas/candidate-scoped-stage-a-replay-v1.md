# Candidate-scoped Stage A successor replay v1

`legalforecast.candidate_scoped_stage_a_replay.v1` is the replay-minted plan that classifies an authenticated predecessor Stage A lineage against successor packet inputs. The predecessor lineage itself is mint-only through `bind_predecessor_stage_a_lineage`, which deep-freezes and commits the exact unitizer envelopes, audits, reviewer flags, packet identities, live Cycle 1 namespace pair `claim-ontology-v5` (unitizer) plus `claim-ontology-v4` (reviewer), shared provider-caps digest, provider-journal path, and predecessor selection/materialization/parser digests. Direct construction of the predecessor, plan, rerun request, execution, or receipt is rejected. The plan binds that predecessor digest together with the successor selection, materialization, and parser digests. Each candidate is classified `reused` when its packet-input identity is unchanged, or `rerun` when selection, source-document bytes, or parser-output identity changed. The plan covers every predecessor candidate in predecessor order. A subset, extra candidate, or hand-authored exact-100 lineage fails closed. Execution is one-shot: a minted plan cannot be run again, and an identically re-minted plan with the same `plan_sha256` in the same process is also consumed, so an `unknown` outcome is permanently nonretryable.

Packet-input identity is the named `legalforecast.commitment.artifact-canonical-json.raw-sha256.v1` digest, domain-separated by `legalforecast.candidate_scoped_stage_a_replay.v1`, over an artifact-canonical JSON object containing exactly `candidate_id`, `case_id`, `selection`, `documents`, and `parser_outputs`. Document rows contain `source_document_id`, `document_role`, `sha256`, and `byte_count`. Parser rows contain `source_document_id`, `markdown_sha256`, and `parser_reuse_identity_sha256`.

The planner is observational. It opens no provider journal, constructs no transport, and grants no execution, purchase, freeze, dispatch, or publication authority. Shared caps and journal identity are required: a different caps digest or journal path fails closed rather than silently opening a new spend namespace. Namespaces other than the live v5/v4 pair, including v4/v4, v5/v5, omitted, and historical pairs, are rejected on this path.

`legalforecast.candidate_scoped_stage_a_replay_receipt.v1` is the sealed complete successor Stage A lineage. Reused candidates keep the predecessor unitizer envelope, audit, and reviewer flags byte-for-byte. Rerun candidates receive injected unitizer then reviewer results through a replay-minted request that binds the successor packet identity, plan digest, v5/v4 namespaces, and shared caps/journal; the returned outcome must echo that `request_sha256`. Timing is monotonic per candidate (`elapsed_ms`, `unitizer_elapsed_ms`, `reviewer_elapsed_ms`). Reused candidates record zero elapsed time. Terminal predecessor statuses (`reconstruction_failed`, `terminal_escalation`) are not retried when packet inputs match; a changed packet is rerun even if the predecessor was terminal. A terminal unitizer result records reviewer status as that same terminal status so the sealed lineage can rebind as a later predecessor. Stage outcomes must carry matching nested `candidate_id` values. Injected rerun outcomes must also echo the replay terminal `status` on their audit. Predecessor live audits keep the Stage A vocabulary (`succeeded` / `adjudication_pending` for the unitizer, `passed` / `flags_pending` for the reviewer) and must be compatible with replay terminal state (`settled`, `reconstruction_failed`, `terminal_escalation`). An `unknown` audit cannot bind. The reviewer receives a detached copy of the unitizer outcome; mutations of that copy cannot enter the sealed unitizer payload. An `unknown` rerun outcome is permanently nonretryable, stops later rerun callbacks, and cannot seal. Plan consumption is claimed under a lock before callbacks, so concurrent `run` invocations cannot double-spend. Sealing recommits the execution payloads and deep-freezes the receipt mappings; `to_record()` fails closed if those payloads later change. Sealing requires every candidate to be `settled`, `reconstruction_failed`, or `terminal_escalation`, and the sealed candidate set must equal the predecessor set in predecessor order.
